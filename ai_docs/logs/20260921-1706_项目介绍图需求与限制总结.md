# Crazy Luna v2.0 项目介绍图需求与限制总结

## 1. 文档目的

本文汇总本次对话中提出的全部项目介绍图要求，并将多轮调整后的内容重建为一份可直接用于重新生成、修改和验收图片的当前规格。

文档分为两部分：

- **当前有效规格**：后续制作图片时应遵守的最终要求。
- **需求演进记录**：说明图片从最初版本到当前版本经历了哪些调整；被后续要求替代的布局不再作为当前约束。

## 2. 图片目标

为 Crazy Luna v2.0 的 README 制作一张清晰说明工作机制的项目介绍图，重点表现：

1. 用户如何通过一句话启动 Luna Keeper。
2. Keeper 如何借助 Roadmap 完成任务分析与拆解。
3. Keeper 如何新开执行对话并启动执行者。
4. 执行者如何分派、跟进和汇总多个执行子 Agent。
5. 结果与证据如何逐层返回，最终交付给用户。
6. Astra/Sol、Terra、Luna 三类模型分别承担的层级和职责。

图片应优先保证流程关系直观、信息层级明确和文字可读，不追求堆叠更多说明元素。

## 3. 当前参与方

### 3.1 用户

- 用一句话向 Keeper 启动任务。
- 接收 Keeper 的完成通知。
- 接收最终的“任务执行结果”文档。

### 3.2 Keeper 总推进

- 接收用户的任务启动请求。
- 请求 Roadmap 分析任务并拆解方案。
- 接收 Roadmap 返回的任务卡片和 prompt 指令。
- 新开执行对话并启动执行者。
- 向执行者传递方案与 prompt 指令。
- 接收执行者返回的结果与证据。
- 向用户交付完成通知和任务执行结果。

### 3.3 Roadmap 拆解任务

- 分析任务目标和上下文。
- 拆解可执行方案。
- 向 Keeper 返回任务卡片和 prompt 指令。

### 3.4 执行者

- 由 Keeper 启动，并在“新对话窗口”中持续推进任务。
- 接收 Keeper 的方案。
- 分派子 Agent 任务。
- 整合修改并总结执行结果。
- 将结果反馈给 Keeper。
- 接收并处理返工要求。

图片中执行者右侧必须保留以下原文：

```text
执行者由Keeper启动，自动执行下列任务：
1. 接收 Keeper 的方案。
2. 负责分派子 Agent任务、整合修改、总结执行结果。
3. 将结果反馈给Keeper，并处理返工要求。
```

这段说明使用较小字号，保持可读但不抢占主流程视觉。相对于最初加入时的字号，经历了两次“缩小 50%”调整，最终应作为明显的次级说明文字。

### 3.5 执行子 Agent

执行子 Agent 使用旧版本中清晰列出多种类型的表现方式，但从左到右横向排列：

1. 写代码
2. 跑测试
3. 查问题
4. 独立验收

每个子 Agent 方块均保留“轻量模型”标签。“独立验收”属于执行子 Agent 类型之一，不再作为主流程中的独立一级参与方。

## 4. 总体关系

核心关系为：

```text
用户 ⇄ Keeper 总推进 ⇄ 执行者 ⇄ 执行子 Agent
           ⇄
   Roadmap 拆解任务
```

流程既包含向下的方案、指令和任务派发，也包含向上的任务卡片、产物、验收、结果与证据回传。

## 5. 1–8 完整流程

| 编号 | 方向 | 传递内容 | 颜色 |
| --- | --- | --- | --- |
| 1 | 用户 → Keeper | `使用Luna Keeper完成上面讨论的方案` | 蓝色 |
| 2 | Keeper → Roadmap | `分析任务 · 拆解方案` | 蓝色 |
| 3 | Roadmap → Keeper | `任务卡片 · prompt指令` | 橙色 |
| 4 | Keeper → 执行者 | `方案与prompt指令` | 橙色 |
| 5 | 执行者 → 执行子 Agent | `派发任务` | 蓝色 |
| 6 | 执行子 Agent → 执行者 | `产物与验收` | 绿色 |
| 7 | 执行者 → Keeper | `结果与证据` | 绿色 |
| 8 | Keeper → 用户 | `上述方案已完成`，并附带“任务执行结果”文档 | 绿色 |

所有编号圆圈均使用实心圆和白色数字：

- 1、2、5：蓝色实心圆。
- 3、4：橙色实心圆。
- 6、7、8：绿色实心圆。

`prompt` 在步骤 3 和步骤 4 中均使用小写英文。

## 6. 用户与 Keeper 的对话表现

用户和 Keeper 之间使用真实对白，不使用抽象的“目标与控制”“进度与交付”等概念文案。

### 6.1 启动任务

用户原话：

```text
使用Luna Keeper完成上面讨论的方案
```

使用漫画式圆角对白气泡表现。布局顺序为：

```text
用户 → 对话气泡 → 编号 1 的蓝色箭头 → Keeper
```

气泡放在箭头之前，不与箭头采用上下堆叠，避免第一层臃肿。

### 6.2 完成任务

Keeper 原话：

```text
上述方案已完成
```

同样使用漫画式圆角对白气泡。布局顺序为：

```text
Keeper → 对话气泡 → 编号 8 的绿色箭头 → 用户
```

除对白外，还需交付一个绿色文档图标，文档名为：

```text
任务执行结果
```

“任务执行结果”的字号应比主流程文字小，作为次级交付信息。此前已要求约缩小 25%，避免抢夺视觉焦点。

## 7. 三层模型结构

三层均使用大面积、低饱和、圆角背景框划定模型层级，并拉开层间距。

### 7.1 第一层

标题必须为：

```text
第一层 · Astra/Sol 聪明模型 · 规划
```

第一层只保留两个主模块：

- 左侧：`Keeper 总推进`
- 右侧：`Roadmap 拆解任务`

两个模块在第一层内左右均衡分布。

用户不属于第一层背景框。用户卡片应独立放在整个三层模块的左侧，并位于所有三层背景框之外。用户外侧不得再增加贯穿三层高度的独立大框，以免被理解为第四层。

### 7.2 第二层

标题必须为：

```text
第二层 · Terra 模型 · 任务跟进
```

- 执行者位于 Keeper 正下方，两者中心线严格纵向对齐。
- 执行者使用带窗口控制点和对话图标的“新对话窗口”卡片。
- 执行者右侧放置工作和责任说明。
- 步骤 4 和步骤 7 必须直接连接 Keeper 卡片与执行者卡片，不能停在第一层或第二层背景框边界。

步骤 5、6 与执行者之间要保留足够留白。不要让编号和箭头紧贴执行者窗口；应通过较长的垂直连接线表现跨层派发与回收。

### 7.3 第三层

标题必须为：

```text
第三层 · Luna 模型 · 大量执行
```

四个子 Agent 在第三层中从左到右横向排列。执行者位于它们上方。

第三层包含两条严格分离的横向总线：

1. 上方蓝色总线：负责向子 Agent 派发任务。
2. 下方绿色总线：负责接收子 Agent 返回的产物与验收结果。

每个子 Agent 方块上方必须同时存在两条独立纵向箭头：

- 蓝色箭头：从上方蓝色横线向下，箭头终点指向子 Agent 方块上沿。
- 绿色箭头：从子 Agent 方块上沿向上，箭头尖端终止在下方绿色横线上。

绿色箭头的硬性限制：

- 终点必须是绿色横线。
- 不得触碰、穿过、覆盖或终止在蓝色横线。
- 绿色箭头尖端不得出现在绿色线与蓝色线之间。
- 四条绿色箭头的终点高度必须一致。

## 8. 对齐与版式限制

1. 用户独立位于三层模块左侧。
2. 三个层级大框的左右边界保持一致，形成统一的纵向系统区域。
3. 第一层 Keeper 与 Roadmap 左右均衡摆放。
4. 第二层执行者与第一层 Keeper 上下对齐。
5. 第三层四个子 Agent 等间距横向排列。
6. 各层之间保持明显留白，不让编号、箭头或模块拥挤在层边界附近。
7. 箭头必须连接实际参与方卡片，背景层大框只表示模型层级，不作为连接对象。

## 9. 视觉风格

整体风格参照最初提供的 Crazy Luna v2.0 项目介绍图：

- 白色背景与浅蓝色细网格。
- 蓝色、橙色、绿色、紫色组成的清晰流程配色。
- 圆角卡片、细描边和克制的柔和阴影。
- 统一的立体机器人图标风格。
- 文字清晰、锐利，不变形、不重影。
- 信息层级明确，避免说明文字过多造成画面混乱。
- 主流程和参与方名称优先，责任说明与文档名称弱化处理。
- 标题保持：`Crazy Luna v2.0`。
- 副标题保持：`Luna Keeper × Luna Roadmap`。

当前最终图片画布为 `1536 × 1024` 横向 PNG。后续重新生成时应保持相同纵横比和高清可读性。

## 10. 图像质量与重新生成限制

图片经过多轮生成或编辑后，容易积累残影、斑块、脏污、模糊边缘和不一致纹理。后续制作必须遵守：

1. 大范围重排或整体质量下降时，从最初的干净原图重新生成，不继续在最新退化图片上反复覆盖。
2. 干净原图只用于视觉风格和质感参考；当前版本用于内容与布局参考。
3. 保留所有已经确认的内容和结构变化。
4. 清除幽灵阴影、色块、脏斑、重复线条、接缝和不一致渐变。
5. 当修改仅涉及局部元素时，避免全局重绘。
6. 未修改区域应尽量与干净来源保持视觉一致。
7. 卡片、文字、线条和阴影应重新绘制得清晰统一，而不是简单放大旧位图。
8. 输出需要在 100% 缩放下仍保持文字、箭头和边界清晰。

## 12. 需求演进记录

1. 最初图片采用“提出目标—自动交接—分工执行”的三栏项目介绍结构，信息较多但参与方和消息流不够直观。
2. 先梳理出用户、Keeper、执行协调者、执行子 Agent 和独立验收等参与方，并明确每一方的职责。
3. 主关系简化为“用户 ⇄ Keeper → 执行者 → 执行子 Agent”，结果与证据逐级返回。
4. 布局从三栏横排改为上下分层，并要求执行者与 Keeper 对齐。
5. 用户和 Keeper 之间的抽象标签改为真实对白，并使用漫画对白气泡。
6. Keeper 向用户的返回内容增加“任务执行结果”文档。
7. Keeper 右侧增加 Roadmap 模块，形成任务分析、拆解和任务卡片返回关系。
8. 执行者改为“新对话窗口”表现方式。
9. 执行子 Agent 恢复为“写代码、跑测试、查问题、独立验收”四种类型，并改为横向排列。
10. 所有主要连线增加 1–8 顺序编号，并统一颜色语义。
11. 步骤 3 和步骤 4 的文案明确为 `prompt指令`。
12. 增加 Astra、Terra、Luna 三层模型背景框，并进一步改为 Astra/Sol、Terra、Luna。
13. 修正步骤 4、7，使箭头直接连接 Keeper 和执行者，而不是停在背景框边界。
14. 调整步骤 5、6 与执行者之间的间距，增加跨层留白。
15. 缩小“任务执行结果”和执行者责任说明的字号。
16. 调整步骤 1、8 的气泡与箭头关系，避免上下堆叠造成臃肿。
17. 将全部 1–8 编号圆圈统一为实心圆。
18. 将用户移出第一层，放到整个三层系统左侧；第一层仅保留 Keeper 与 Roadmap。
19. 对齐三层大框边界，并保持 Keeper 与执行者的纵向对齐。
20. 从干净原图重新绘制高清版本，消除多轮编辑形成的残影和斑块。
21. 最后修正第三层绿色返回箭头，使其终止在绿色横线而非蓝色横线。
