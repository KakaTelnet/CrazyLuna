### 3.1 测试脚本结构

1. 使用 `require_relative 'validate'`，根据 `__dir__` 定位 Skill 根目录，读取当前包文件组成 documents；沿用校验器的包内相对路径口径。不能依赖调用者工作目录。
2. 基线从真实包读取，不另复制一套长期 fixture。每个用例使用独立 Hash 和字符串副本，变异只发生在内存，不写回运行包。
3. 用简单的用例表和局部辅助方法表达 16 个场景。YAML 变体通过标准库解析、修改和重新序列化；围栏和 frontmatter 定位须明确命中，避免静默替换失败。
4. 保留原始基线用于 C01。每个负例只引入对应故障；用例构造失败属于测试失败，不能按“预期拒绝”通过。
5. 接受用例必须确认 `validate` 返回 `true`。拒绝用例必须捕获 `CrazyLunaValidation::Invalid`，并检查对应错误类别前缀或关键片段；不逐字锁定整段报错。其他异常均记失败并显示原因。
6. 输出各用例 ID、名称和 PASS/FAIL，以及总数、通过数、失败数。全部通过退出 0；任何断言或构造失败退出非零。可继续运行其余用例后汇总，不吞掉失败。
7. 只测试已有规则，不实现模型可用性解析、配置持久化或行为评估。无需新增配置、命令行参数、自动运行钩子或测试依赖。

调用关系：维护者运行 `test_validate.rb` → 读取真实包 → 构造内存变体 → 调用现有 `validate(documents)` → 比较预期 → 输出结果与退出码。默认 Skill 调用路径不变。

### 5.2 失败传播验证

为证明测试入口能发现回归，而非只打印成功，使用两个独立 Ruby 子进程做内存故障注入。每个进程先 require 真实 `validate.rb`，临时覆盖 `CrazyLunaValidation.validate`，再 load `test_validate.rb`：

1. 覆盖为恒定返回 `true`：拒绝场景必须出现 FAIL，整个进程退出非零。
2. 覆盖为恒定抛 `CrazyLunaValidation::Invalid`：接受场景必须出现 FAIL，整个进程退出非零；无关错误原因也不能使所有拒绝场景误通过。

可用 Ruby `Open3.capture3` 以参数数组调用 `RbConfig.ruby`，捕获退出码及输出。只在子进程内替换方法，不修改生产文件，不保存故障注入脚本或 fixture；这属于验收操作，不新增测试框架或公共接口。命令拼接不得依赖易出错的 shell 引号。真实回归入口正常运行仍须退出 0。

返工只处理范围内问题；若必须修改校验器、依赖或既有产品规则，先记录实际差异与原因，交回规划者或用户确认修订范围。修改会影响哪些 AC 必须查明，并重新验收；影响不明时暂停相关完成判定。重复失败无新证据、修复不收敛或设计前提失效时暂停受影响任务，报告已尝试内容与证据。

续接先核对方案、记录、文件和在途 Agent，避免重复派发。全部必需 AC 通过、最终版本一致、范围和基线保护核对完成后，才宣布本轮调整完成。交付报告列出文件、命令结果、独立验收结论和未验证边界，不自动 commit、push 或发布。
