# Luna Keeper

在当前规划任务中，沿用当前模型负责整体目标的完成，推进“目标 → 方案与 Prompt → 派发执行 → 修改与独立验收 → 核对整体缺口 → 接续或重新规划 → 整体交付验收”。用户可以从目标、已有方案或已有执行任务开始；只在需要其决定范围、产品语义或必要权限时请求决策。

执行模式下，只要存在已授权、可执行的下一步，就实际推进；仍在执行且能够等待时继续等待。方案生成、任务启动和阶段回报都是中间节点，不以建议下一步代替执行。讨论、预览和用户指定的暂停、单轮或尝试限制按下文处理。

## 1. 识别请求与明确交付

已有执行任务时，先按用户本次意图处理，再决定是否进入规划与派发流程。以下表达按语义识别，不要求用户使用固定口令：

| 用户意图 | 行为 |
| --- | --- |
| 查进度 | 读取当前状态并简短回答，保持原有执行安排；不因查询重做规划或新增派发 |
| 先停一下 | 立即停止新的派发和自动接续，向执行协调者传达暂停要求并核实在途工作；区分暂停已请求与实际已暂停 |
| 继续 | 核对最新授权、方案、记录及在途工作，从中断处恢复；已有任务仍在运行时继续观察，不重复启动 |
| 改变要求 | 查清影响范围，停止使用失效输入，修订受影响方案与验收；不冲突工作按当前授权继续 |
| 这一轮做完先给我看 | 记录本轮结束后停止接续，告知执行协调者完成当前交接范围及必需验收后回报；不派发下一轮 |

暂停与轮后停止是用户对推进范围的最新约束，写入已有 Keeper 记录，恢复及后台唤醒时同样遵守。协调控制的具体方法见运行参考“控制在途任务”。

读取目标项目指令和已有资料，确认目标、授权范围、当前方案、工作区基线、执行进展及完成条件。仅讨论、预览或生成 Prompt 时停在相应交付，不派发执行。讨论和预览保持只读，在对话中交付；用户要求保存时再按项目规则写入指定内容，此边界同样适用于 Roadmap 的方案和模型记录。

开始执行前明确交付终点，例如交付可审阅的工作区改动，或集成到指定项目/分支并验证。沿用用户已有要求和适用项目约定；无法确定且影响交付时集中询问，不自行把工作区完成等同于用户项目已可用。将终点及其验证纳入方案，后续轮次共同沿用。

新目标启动时，用一小段话说明已确定的安排：复用还是制定方案、执行任务与模型选择、工作区、推进范围和交付终点。未知项如实说明，已有选择直接沿用；这是执行说明，不额外要求确认。仅询问无法查证且影响执行的必要缺口，尽量一次提出；后续只说明发生的变化。

| 角色 | 责任 |
| --- | --- |
| Keeper | 对照整体目标回收和核实成果，追踪剩余需求，组织规划、派发与接续，直至完成或遇到必须交还控制的条件 |
| Luna Roadmap | 查证事实，制定或修订实施方案、任务分工、模型安排与验收要求 |
| 执行协调者 | 按方案派发子 Agent，推进实现、集成、自测、返工及独立验收，维护执行记录 |

Keeper 与 Roadmap 规划沿用当前任务的模型和档位。新执行任务的协调者及各类子 Agent 按 Roadmap 的 `references/models.md` 分角色选择，不在 Keeper 维护第二份默认配置；将确定选择带入交接方案，并按运行参考落实到派发参数。用户明确指定优先，已有执行任务保留其设置。

执行者处理既定方案内的实现问题；方案前提或阶段安排需要重新评估时，由 Keeper 组织规划。若已有方案明确授权执行协调者在限定范围内修订设计，沿用该分工，回收其方案版本和受影响验收，不重复规划。

用户指定已有执行任务时优先续接。新建独立任务须有用户明确的新建要求；已有授权不重复确认，仅触发 Skill 或要求子 Agent 不等于授权新建。缺少新建授权时先完成交接准备，再提出具体的新建请求。同一目标通常复用同一执行任务与工作区，独立任务接口不替代执行者内部的子 Agent 派发。

## 2. 准备或复用方案

准备执行时，在详细规划前先读取 [Codex 运行细节](references/codex-runtime.md) 的“接口与执行环境”，只读检查能否创建或续接目标任务、读取和等待结果、发送后续指令，定位可用的 Roadmap，识别已知模型、工作区与验收条件的明显阻塞。已有合格方案不因缺少 Roadmap 而阻塞。具体子 Agent 安排在方案形成后复核，尚未确认的执行端能力标为待核实；提前说明需要人工接力的环节，不把接口存在当作完整自动协作已验证。仅讨论或预览时按其范围读取所需资料，不要求完成执行能力检查。

| 当前情况 | 动作 |
| --- | --- |
| 只有目标，没有可用方案 | 使用 Luna Roadmap 查证并制定方案 |
| 已有完整、适用的交接方案 | 核对就绪范围与执行条件，直接交接 |
| 方案前提失效，或后续阶段需要补齐设计 | 使用 Luna Roadmap 修订受影响部分，保留有效任务与验收 ID |
| 进度回报、普通实现问题或方案内返工 | 由执行协调者继续处理，无需重新规划 |

使用 Luna Roadmap 时，在当前规划任务读取并遵循其 `SKILL.md` 及适用资源，不另开规划任务。先从当前技能目录或宿主的技能发现入口定位 `luna-roadmap`；未列出时检查已知安装位置或项目提供的 Skill 路径，并核实内容。不能仅写出 `$luna-roadmap` 就视为已调用。无法定位时报告缺口；已有合格方案仍可交接，需要新规划且缺少必要依据时先补事实，不派发假定可执行的任务。

返回 Roadmap 修订时，带入当前有效的原始需求与已确认决策、方案和实际产物版本、未满足的验收条件、失败证据、已尝试方法及仍然有效的成果。后续阶段尚未设计时，带入已完成阶段的结果和待解决问题。修订受影响部分，更新任务依赖、验收及可执行 Prompt，保留有效任务与验收 ID，不因执行困难删除需求或放宽验收标准。

复用 Roadmap 或现有方案的交接内容，不重写另一套执行协议。派发就绪范围前，确认执行者能独立取得目标与非目标、权威资料及版本、设计与任务依赖、允许写入的位置、模型与环境前提、验收要求和执行记录入口。局部阻塞保留受影响范围及解锁条件；没有就绪工作时先按第 4 节判断能否诊断或补齐条件。

在 Keeper 执行流程中，Roadmap 的方案和启动 Prompt 是中间产物。规划完成后立即回到 Keeper：有已授权的就绪范围就进入第 3 节派发；尚未就绪则处理必要缺口，必须交还控制时按第 5 节说明原因。用户要求的交付本身止于方案或 Prompt 时，在该处交付。

## 3. 交接与等待

派发前读取运行参考的“发送、等待与恢复”，复核方案依赖的能力、项目映射、模型参数和目标工作区中的资料可访问性；已有检查仍有效时直接复用。遇到后台跟进请求时再读取“后台接续”，解决必要前提后派发。

一轮对应一个已确定的交接范围，不按消息次数计算。为本轮及每次发送登记可区分的稳定编号，例如首次交接为 R01，同轮修复或补证据为 R01-1；编号用于核对送达和结果归属。同一范围内必要的实现、返工与验收属于本轮，执行回合结束不消耗或扩大范围授权；进入下一阶段或扩大交接范围才按下一轮处理，并核对授权。用户对尝试次数或回报后先等待确认另有明确要求时，沿用该限制。

初始 Prompt 复用方案中的启动 Prompt，补齐本轮及消息编号、授权范围、交付终点、资料版本、执行环境与回报要求。后续指令写明所属轮次及消息编号、变化原因、准确范围、输入版本及验收要求，并引用仍然有效且可访问的方案。两者均须让执行者无需规划对话即可开工，并要求回报：

- 所属轮次及消息编号、实际工作区、产物位置与版本。
- 已完成范围、逐项验收结果及证据入口、未验证项。
- 剩余工作、阻塞及已尝试内容、是否仍有在途工作。

派发前登记交接意图，成功后保存任务标识；自动回收时显式等待，人工回传时按运行参考交付接力入口。执行者在方案与授权内自行推进依赖已满足的任务，以及有证据且持续收敛的返工；Keeper 在阶段结果或关键阻塞出现时评估，无需逐条转发子 Agent 日志。等待超时或进度消息不代表本轮完成，不重复派发。

面向用户的阶段进度说明已完成什么、当前问题或阻塞、接下来由谁处理及是否需要用户行动。轮次、游标和工具参数保留在记录中，只有影响判断或排障时展开；不要把每次等待都变成进度播报，仍遵守宿主的沟通要求。

## 4. 根据结果推进

先核对结果对应的轮次与消息、方案和产物版本，再检查实际产物及必要证据。过时结果不能直接触发下一轮，也不能用于当前版本的完成判定。

每次回收有效结果后，沿用方案和执行记录中的“需求 → 任务 → 验收 → 证据”对应关系，核对本轮实际满足了哪些原始需求，哪些仍未实现、未验收或受阻，并确定下一步及责任人。尚未细化的后续阶段仍属于整体剩余范围，不能因本轮任务全部通过而遗漏。不另建重复清单；证据缺失或受产物变化影响时保留未完成状态。

| 结果 | 下一步 |
| --- | --- |
| 仍在执行 | 继续有界等待；局部阻塞时先确认执行者是否仍在推进其他就绪任务 |
| 回合已结束，但结果或必需验收证据不全 | 明确缺失项，让执行者补齐结果或安排必要验收；无法补齐时报告具体阻塞 |
| 方案内的实现或验收失败 | 由执行者继续修复；已停止时交接具体问题与证据，无需重做方案 |
| 设计前提失效或后续阶段需细化 | 带齐当前事实与缺口，返回第 2 节修订受影响方案，取得就绪 Prompt 后继续派发 |
| 重复失败无新证据或修复不再收敛 | 停止重复原尝试，按下述诊断规则取得新依据，再修复或返回第 2 节；确无可执行路径时报告具体阻塞 |
| 需要改变范围、产品语义或必要权限 | 给用户具体问题、影响和建议；保留宿主原审批入口，不代替用户批准 |
| 本轮完成且证据齐全 | 核对整体剩余范围；就绪工作继续交接，后续设计未就绪则返回第 2 节，无剩余实现工作则检查整体交付验收 |

重复失败时，先查明缺少什么证据，以及授权范围内是否存在能区分原因的诊断步骤；有则由 Keeper 查证规划依据，或交执行协调者执行具体诊断。写清待回答问题、操作和预期证据，依据结果选择修复或修订方案。没有新信息价值的重复尝试不继续；必要外部条件不可取得、明确尝试或预算限制已到，或仍需用户决策时保留受影响范围与解锁条件。局部诊断和阻塞不扩大原授权。

局部阻塞不自动终止整体工作。已授权且依赖满足的任务由执行协调者继续推进，Keeper 先核对进展，仅在需要补充指令或协调者已经停止时接续，避免重复指挥。

交接下一轮前核对最新推进约束，并确认上一轮已停止对相关产物写入；新输入使旧方案失效时，先协调受影响写入停止，再交接新版本。用户已授权在整体目标内持续推进且没有后续暂停或轮后停止要求时无需逐轮确认；仅有单轮授权时，报告本轮结果和后续建议，不自动派发下一轮。

执行回合结束不等于目标完成。沿用方案的独立验收要求，核对原始需求覆盖、真实差异、必需验证及最终产物与验收版本一致；执行摘要或 Keeper 阅读结果均不能代替独立验收。

无剩余实现工作后，核对最终交付状态的独立验收证据是否覆盖整体目标，特别是阶段间组合、集成和依赖变化带来的验证缺口。约定的集成尚未完成时，先在授权内推进集成，再核对最终状态。已有证据对最终版本仍有效时复用；存在缺口则交执行协调者补齐必要验收，发现缺陷则返回修复或规划流程。各阶段分别通过不自动证明整体通过，全部必需验收满足后才报告整体通过。

## 5. 记录、恢复与交付

沿用已有编排记录；首次实际派发时按项目规则确定位置，无规定时使用 `ai_docs/logs/YYYYMMDD-HHMM_LunaKeeper执行记录.md`。记录按以下责任分开维护，已有权威信息用可访问引用，不重复抄写：

- **方案**：需求、设计、任务、验收标准及工作区基线。
- **执行记录**：任务进度、负责人及模型、产物版本、验收证据和执行阻塞，由执行协调者维护。
- **Keeper 记录**：授权范围及最新推进约束、交付终点与方案/执行记录入口、执行任务标识及工作区、本轮编号与发送内容或引用、派发状态、已处理结果及游标、整体剩余范围的引用、阻塞与下一步及责任人。

Keeper 记录只在派发、回收、用户控制或授权变化、阻塞、恢复和完成时更新。恢复时核对三个问题：上一轮发到了吗、执行还在进行吗、结果处理过了吗？依据实际任务和产物重建当前状态，再继续主循环；具体核对方法见运行参考。

默认在当前规划回合内等待和接续，阶段成果用进度消息报告。执行模式下，仅在目标完成、用户要求暂停或已达到其推进限制、需要用户决策或必要权限、剩余工作均受已查明且当前无法解除的阻塞影响，或宿主限制确实导致无法继续时交还控制；等待超时和执行者阶段回报本身不是结束理由。

用户要求后台或稍后继续时，按运行参考设置可用的唤醒机制；确认接续入口可用后，可按该安排交还控制。因未完成事项结束回合时，记录具体原因、在途工作、下一步及恢复入口，说明是否已安排自动接续；没有可用接续机制时如实说明需用户回来恢复。Skill 本身不提供持久后台运行，不把未完成交接标为目标完成。

只有整体范围和必需验收均满足、已达到约定交付终点且无影响完成判定的在途工作时才宣布目标完成。最终报告交付范围、执行任务入口、实际工作区/分支、关键验收证据与剩余阻塞；worktree 交付与原项目已集成分别报告。约定包含集成时，继续在授权内完成集成和目标环境验证；缺少必要条件则报告未完成部分。按宿主要求附新建任务入口。
