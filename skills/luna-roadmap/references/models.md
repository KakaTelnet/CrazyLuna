# 模型配置

```yaml
roles:
  coordinator:
    model: gpt-5.6-terra
    reasoning_preference: medium
  worker:
    model: gpt-5.6-luna
    reasoning_preference: medium
  verifier:
    model: gpt-5.6-luna
    reasoning_preference: medium
alternative_models:
  - claude-haiku
  - deepseek-v4.1-flash
```

## 选择规则

- Keeper 和 Roadmap 规划沿用当前任务的模型与档位，由用户控制。`coordinator` 仅用于新建执行任务；已有执行任务保留其设置，用户明确要求调整时再改。`worker` 用于实施、测试与诊断子 Agent，`verifier` 用于未参与产物制作的独立验收子 Agent。
- 模型和档位分别按「本轮角色指定 → 本轮明确适用于该角色的通用指定 → 对应角色配置」选择；不能把用户为协调者指定的 Terra 传播给全部子 Agent。临时覆盖不修改长期配置。三个角色均须配置精确模型 ID 和 `medium` 或 `high` 偏好；其他宿主或用户指定的型号、档位按当前接口核实。
- 未显式固定档位时，以角色配置为起点，按下表决定是否需要 `high`。方案须给出每个角色或任务的确定模型、确定档位及简短理由，不保留“medium 或 high”待执行者猜测。任务多、文件多或日志长本身不是升档依据。
- `alternative_models` 仅列出可由用户明确选择的其他候选，不参与默认自动替换。选定模型或档位不可用时，说明具体缺口及可选安排，不静默换型、降档或省略参数退回宿主默认。用户另有明确候选与替换规则时按其执行。
- 从当前宿主声明、派发工具及 schema 核对精确 ID、工具、输入、上下文和推理参数；主任务支持不代表子 Agent 可用。配置是选择策略，不越过宿主的模型授权要求；接口要求用户明确指定型号时，核对已有指定，缺少则先准备具体选择再集中询问。只读取必要非敏感信息，不主动付费探测或改宿主配置。
- 推理档位映射须有证据；参数未解析或档位无法满足时，阻塞受影响派发。宿主不支持显式调档时，说明实际限制，取得用户对宿主默认档位的接受后才省略，并将实际档位标为未知或宿主已确认值。
- 执行失败先区分环境、权限、输入、方案与判断能力问题；前四类优先解决原因。仅有证据表明判断能力不足，且方案已授权升档时，才从 `medium` 提升至 `high`，记录原因并只重做受影响工作。显式固定档位不自动升级；`high` 仍失败则按执行协议诊断或交回规划，不自动换更贵模型。
- 每次调用复核；方案记录各角色精确 ID、请求档位、实际派发参数、理由、限制、证据及授权的失败后规则。请求值与宿主实际回报分别记录，实际型号或档位未回报则标为未知。无派发能力时按入口说明交接手动会话。

| 角色 | 需要 high 的判断依据 |
| --- | --- |
| 执行协调者 | 多模块依赖尚需协调、集成冲突或诊断需要较多判断 |
| 实施子 Agent | 任务内算法、状态逻辑或边界条件复杂，详细方案仍留下较多实现判断 |
| 独立验收子 Agent | 跨模块行为、复杂回归或证据之间的关系需要较多判断 |

ID 线索：Terra 与 Luna 分别核对接口暴露的 `gpt-5.6-terra`、`gpt-5.6-luna`；Haiku 核对宿主 `haiku` 别名或完整 ID；DeepSeek Flash 核对 `deepseek-flash` 映射。别名、版本和参数均以当前接口为准，不自行替换型号。

## 派发适配

- 将派发接口、模型、推理参数与上下文继承方式作为完整组合核对，不能仅凭模型出现在列表中就判定可派发。例如，若 Codex 接口规定 `fork_turns="all"` 或省略时继承父模型且不接受覆盖，指定 Luna 或推理参数时应显式选择接口允许的 `fork_turns="none"` 或正整数字符串。按所选方式补齐任务卡、权威资料和前置产物，避免依赖未继承的规划对话；其他宿主使用其实际参数。
- 核对工具的派发前提、上下文隔离要求、并发计数口径和剩余名额。若接口仅允许与协调者有效工作并行的独立子任务，方案应同时明确协调者可推进的实际工作；纯等待或存在依赖的工作不算独立并行。串行依赖与名额充足都不能替代派发前提。标为可自动执行前，须确认从实施到独立验收均有满足派发前提的安排，包括只剩最终验收时的安排。
- 将核实后的接口名称、各角色必要参数、上下文传递方式、派发条件及依据写入交接方案，启动 Prompt 引用其具体位置；无法访问时按入口的交付规则内联必要内容。执行会话启动及实际派发前复核当前接口；宿主或能力变化时重新适配，不直接复用旧参数。接口存在或本地记录为 `ready` 不代表当前任务已满足派发条件。
- 条件不满足时说明具体限制，按实际依赖和宿主能力调整工作安排；协调者可在既定范围内承接工作，独立验收仍须满足原有要求。暂时无名额则等待释放；无派发能力或必要派发条件经调整仍无法满足时，按入口为受影响环节交接手动会话，包括实施完成后无法派发独立验收的情况。手动会话仍无法满足的必要条件保持阻塞，不通过虚构并行工作或放宽验收要求绕过。

## 本地记录

`.luna-roadmap/models.local.json` 是可选的宿主诊断快照，用于排查模型或派发能力的变化。本轮有效参数与结论记录在方案或执行记录中，常规规划无需创建或更新本地快照，也不为此创建目录或 `.gitignore`；已有快照不代替本轮能力核实。

仅在用户要求保留宿主诊断信息或项目约定需要时保存。确认任务、项目指令和写入范围后，在目标项目该文件的顶层 `hosts` 中按宿主保存；讨论或预览遵循入口的只读边界，无具体任务或整体阻塞时不初始化。

每个宿主条目的 `roles` 按 `coordinator`、`worker`、`verifier` 分别记录长期配置的核实结果。各角色包含：

- `status`：`ready`、证据不足的 `unknown`、确认不可用的 `unavailable`。
- `allowed_models`、`reasoning_preference`：对应角色配置的模型单项列表与档位偏好，不含临时覆盖和未选用的其他候选。
- `dispatch_supported`：有接口/无接口/未知对应 `true`/`false`/`null`。
- `available_models`：仅含可派发候选，各含 `request_model`、`reasoning_parameters`、`capabilities`、`evidence`。
- `default_model`、`reasoning_parameters`、`selection_reason`：长期默认精确 ID、实际参数及理由。
- `evidence`、`checked_at`、`runtime_model`、`runtime_reasoning`：来源、检查时间、实际回报型号与档位；未回报值为 `null`。

模型或长期参数不可用、无接口时，将对应角色记为 `unavailable`；证据不足记 `unknown`。这两种状态将该角色的默认及实际参数置 `null`，保留原因；旧选择可记 `last_selection`。角色状态不能互相替代，当前任务能否自动执行仍按实际所需角色和用户覆盖判断；临时覆盖、复杂任务选择 high 及实际派发结果记入方案或执行记录，不覆盖长期默认。

读取旧记录时保留宿主原有字段及其内容；缺少 `roles` 表示尚未按角色核实，仅在需要保存快照时重新检查后补入，不将旧的单一默认套给三个角色。旧字段仅保留作历史，不参与当前选择；诊断快照不能覆盖本文件的当前配置、用户指定或已有任务设置。

保存前读取旧记录，保留其他宿主和未知字段；核实结果及依据无变化时不重写，也不单独刷新 `checked_at`。JSON 或记录结构损坏时停止保存，不覆盖或另建旁路文件。使用现有工具安全写入；失败时注明未保存，继续用本轮结果规划。保存快照时才将 `models.local.json` 补入 `.luna-roadmap/.gitignore`，保留原内容；本地记录不随包发布。
