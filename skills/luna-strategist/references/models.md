# 模型配置

```yaml
roles:
  strategist:
    model: gpt-6-astra
    reasoning_preference: high
  coordinator:
    model: gpt-6-sol
    reasoning_preference: medium
  worker:
    model: gpt-6-luna
    reasoning_preference: high
  verifier:
    model: gpt-6-luna
    reasoning_preference: high
alternative_models:
  - claude-haiku
  - deepseek-v4.1-flash
```

## 选择规则

- `strategist` 用于制定及修订方案，模型和档位独立于调用任务，按下节落实实际规划模型。Commander 自身沿用当前任务设置。`coordinator` 用于新建执行任务的 Captain；已有执行任务保留其设置，用户明确要求调整时再改。`worker` 用于实施、测试与诊断子 Agent，`verifier` 用于未参与产物制作的独立验收子 Agent。
- 模型和档位分别按「本轮角色指定 → 本轮明确适用于该角色的通用指定 → 角色配置及下表适用的任务选择」确定；不能把用户为某个角色指定的模型传播给其他角色。临时覆盖不修改长期配置。四个角色均须配置精确模型 ID 和 `medium` 或 `high` 偏好；其他宿主或用户指定的型号、档位按当前接口核实。
- 初始分工以角色配置为起点，仅对用户未显式固定的模型或档位应用下表；未命中时使用角色配置。方案须给出每个角色或任务的确定模型、确定档位及简短理由，不保留“medium 或 high”待执行者猜测。任务多、文件多、测试数量多或日志长本身不是换型或升档依据。初始任务选择不构成失败后自动换型或升档的授权。
- `alternative_models` 仅列出可由用户明确选择的其他候选，不参与默认自动替换。选定模型或档位不可用时，说明具体缺口及可选安排，不静默换型、降档或省略参数退回宿主默认。用户另有明确候选与替换规则时按其执行。
- 从当前宿主声明、派发工具及 schema 核对精确 ID、工具、输入、上下文和推理参数；主任务支持不代表子 Agent 可用。配置是选择策略，不越过宿主的模型授权要求；接口要求用户明确指定型号时，核对已有指定，缺少则先准备具体选择再集中询问。只读取必要非敏感信息，不主动付费探测或改宿主配置。
- 推理档位映射须有证据；参数未解析或档位无法满足时，阻塞受影响派发。宿主不支持显式调档时，说明实际限制，取得用户对宿主默认档位的接受后才省略，并将实际档位标为未知或宿主已确认值。
- 执行失败先区分环境、权限、输入、方案与判断能力问题；前四类优先解决原因。仅有证据表明判断能力不足，且方案已授权升档时，才从 `medium` 提升至 `high`，记录原因并只重做受影响工作。显式固定档位不自动升级；`high` 仍失败则按执行协议诊断或交回规划，不自动换更贵模型。
- 每次调用复核；方案记录各角色精确 ID、请求档位、实际派发参数、理由、限制、证据及授权的失败后规则。请求值与宿主实际回报分别记录，实际型号或档位未回报则标为未知。无派发能力时按入口说明交接手动会话。

| 任务情形 | 初始模型与档位选择 |
| --- | --- |
| 执行协调者需要判断多模块依赖、集成冲突或复杂诊断 | 保持 `coordinator` 模型，档位选择 `high` |
| 实施或诊断子 Agent 涉及复杂算法、状态与边界逻辑、未知故障根因或跨模块行为，详细方案仍留下较多实现判断 | 选择 `gpt-6-sol`、`high`；普通实施仍使用 `worker` 配置 |
| 独立验收按明确标准核对需求与差异、运行现有测试、检查退出状态并整理证据 | 使用 `verifier` 配置 |
| 独立验收需要补充复杂验收设计、识别未覆盖的复杂边界、判断跨模块行为或分析复杂失败原因，现有标准与测试结果不足以直接判定 | 选择 `gpt-6-sol`、`high` |

复杂验收中，测试执行与结论审查确有独立分工价值时，可在方案中安排 `gpt-6-luna high` 执行测试、采集证据，由 `gpt-6-sol high` 审查需求覆盖并给出验收结论；模型与档位仍遵循上述用户指定优先规则。结论审查须核对权威需求、实际产物及关联当前版本的原始证据，不能仅凭测试通过或执行者摘要判定完成；证据仍有效时不要求重复运行测试。独立验收者仍须未参与被验收产物制作，并在独立上下文中验收，使用同一型号不影响角色独立性。

ID 线索：Astra、Sol 与 Luna 分别核对接口暴露的 `gpt-6-astra`、`gpt-6-sol`、`gpt-6-luna`；Haiku 核对宿主 `haiku` 别名或完整 ID；DeepSeek Flash 核对 `deepseek-flash` 映射。别名、版本和参数均以当前接口为准，不自行替换型号。

## 规划模型的落实

调用入口先确认具体任务和目标项目，再按上述优先级解析 `strategist` 模型与档位，在正式查证和设计前确定承载方式：

- 当前任务的模型与档位经宿主证据确认符合选定配置时，可直接规划。否则由调用方在授权及下节派发条件满足时，显式指定选定模型与档位派发规划 Agent；不能用 Prompt 宣称当前任务已切换模型。
- 已由调用方按选定参数启动的规划 Agent 直接执行本 Skill，将派发请求与宿主实际回报分别记录；实际值未回报时标为未知，不因此再派发规划 Agent。实际型号或档位不符时报告差异，按已有授权处理，不静默接受替换。规划 Agent 只查证、制定或修订方案、准备执行 Prompt；仅在授权范围内保存规划产物，不修改业务代码、不派发执行或继续创建 Agent，完成后向调用方回报。
- 调用方传入可访问的 Skill 入口及资源、目标项目、有效需求与决策、基线、约束、授权写入范围和交付要求；修订时追加当前方案、产物版本、失败证据及尝试记录。只讨论时沿用只读边界。调用方回收并核对实际方案、需求覆盖、模型安排、就绪范围与阻塞后，再按已有授权交接执行。
- 缺少模型授权、模型或派发能力，或派发条件无法满足时，先报告具体缺口；不能静默继承调用方模型。提供包含选定模型与档位、必要输入及回报要求的手动规划交接；由用户在对应模型的任务中运行。已有完整且适用的方案可直接复用，无需为了采用默认模型重新规划。

## 派发适配

- 将派发接口、模型、推理参数与上下文继承方式作为完整组合核对，不能仅凭模型出现在列表中就判定可派发。例如，若 Codex 接口规定 `fork_turns="all"` 或省略时继承父模型且不接受覆盖，指定 Luna 或推理参数时应显式选择接口允许的 `fork_turns="none"` 或正整数字符串。按所选方式补齐任务卡、权威资料和前置产物，避免依赖未继承的规划对话；其他宿主使用其实际参数。
- 核对工具的派发前提、上下文隔离要求、并发计数口径和剩余名额，规划 Agent 也计入宿主占用。若接口仅允许与调用方有效工作并行的独立子任务，派发前应明确调用方可推进的实际工作；纯等待或存在依赖的工作不算独立并行。串行依赖与名额充足都不能替代派发前提。标为可自动执行前，须确认从规划到实施及独立验收均有满足派发前提的安排，包括只剩规划或最终验收时的安排。
- 将核实后的接口名称、各角色必要参数、上下文传递方式、派发条件及依据写入交接方案，启动 Prompt 引用其具体位置；无法访问时按入口的交付规则内联必要内容。执行会话启动及实际派发前复核当前接口；宿主或能力变化时重新适配，不直接复用旧参数。接口存在或本地记录为 `ready` 不代表当前任务已满足派发条件。
- 收到名额或 Agent 上限错误时，先核对实际占用、在途工作和宿主计数口径，不仅凭错误名称推断限制类型。宿主支持续接时，可复用模型、角色及上下文仍合适的既有 Agent；复用验收者须确认其未参与被验收产物制作，且仍满足独立上下文要求。需要全新无先验上下文的盲测不能复用知情 Agent。只有确认在途工作结束可释放所需名额时才等待；无释放依据且无法复用时，按下述规则处理，不反复尝试新建。
- 条件不满足时说明具体限制，按实际依赖和宿主能力调整工作安排；协调者可在既定范围内承接工作，独立验收仍须满足原有要求。无派发能力或必要派发条件经调整仍无法满足时，按入口为受影响环节交接手动会话，包括实施完成后无法派发独立验收的情况。手动会话仍无法满足的必要条件保持阻塞，不通过虚构并行工作或放宽验收要求绕过。

## 本地记录

`.luna-strategist/models.local.json` 是可选的宿主诊断快照，用于排查模型或派发能力的变化。本轮有效参数与结论记录在方案或执行记录中，常规规划无需创建或更新本地快照，也不为此创建目录或 `.gitignore`；已有快照不代替本轮能力核实。

仅在用户要求保留宿主诊断信息或项目约定需要时保存。确认任务、项目指令和写入范围后，在目标项目该文件的顶层 `hosts` 中按宿主保存；讨论或预览遵循入口的只读边界，无具体任务或整体阻塞时不初始化。

每个宿主条目的 `roles` 按 `strategist`、`coordinator`、`worker`、`verifier` 分别记录长期配置的核实结果。各角色包含：

- `status`：`ready`、证据不足的 `unknown`、确认不可用的 `unavailable`。
- `allowed_models`、`reasoning_preference`：对应角色配置的模型单项列表与档位偏好，不含临时覆盖和未选用的其他候选。
- `dispatch_supported`：有接口/无接口/未知对应 `true`/`false`/`null`。
- `available_models`：仅含可派发候选，各含 `request_model`、`reasoning_parameters`、`capabilities`、`evidence`。
- `default_model`、`reasoning_parameters`、`selection_reason`：长期默认精确 ID、实际参数及理由。
- `evidence`、`checked_at`、`runtime_model`、`runtime_reasoning`：来源、检查时间、实际回报型号与档位；未回报值为 `null`。

模型或长期参数不可用、缺少必要执行途径时，将对应角色记为 `unavailable`；证据不足记 `unknown`。这两种状态将该角色的默认及实际参数置 `null`，保留原因；旧选择可记 `last_selection`。Strategist 可在模型与档位已核实一致的当前任务中直接规划，此时没有派发接口本身不构成不可用。角色状态不能互相替代，当前任务能否自动执行仍按实际所需角色和用户覆盖判断；临时覆盖、按任务选择的模型与档位及实际派发结果记入方案或执行记录，不覆盖长期默认。

读取旧记录时保留宿主原有字段及其内容；缺少 `roles` 或某个角色表示尚未核实该部分，仅在需要保存快照时重新检查后补入，不将旧的单一默认或其他角色结果套给缺失角色。旧字段仅保留作历史，不参与当前选择；诊断快照不能覆盖本文件的当前配置、用户指定或已有任务设置。

保存前读取旧记录，保留其他宿主和未知字段；核实结果及依据无变化时不重写，也不单独刷新 `checked_at`。JSON 或记录结构损坏时停止保存，不覆盖或另建旁路文件。使用现有工具安全写入；失败时注明未保存，继续用本轮结果规划。保存快照时才将 `models.local.json` 补入 `.luna-strategist/.gitignore`，保留原内容；本地记录不随包发布。

## 宿主与校验

保留手动调用策略。运行 `ruby <Skill目录>/scripts/validate.rb` 做静态校验；宿主运行另行实测。
