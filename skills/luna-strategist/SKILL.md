# Luna Strategist

将开发任务整理为可独立执行和验收的交接方案。采用用户的语言。讨论或预览时保持只读，在对话中交付；用户要求保存时按项目规则写入指定内容，此边界同时适用于方案和模型记录。正式交接默认交付方案文档和聊天中的启动 Prompt；生成 Prompt 不启动执行。用户明确要求继续执行时，按已有授权推进。

执行者依据交接方案工作，无需重新调用本 Skill。

正式规划前，调用入口先读取 [模型清单与宿主规则](references/models.md)，按“规划模型的落实”选择直接规划或由指定模型的规划 Agent 承担。规划 Agent 收到本 Skill 后完成方案并回交调用方，不继续派发；模型配置与宿主实际回报分别记录。

## 1. 查证需求与范围

先确认具体任务和目标项目，读取适用的项目指令，查明写入范围；任务或项目不明确时先询问，不创建文档或状态目录。读取权威需求、相关入口、代码、测试和配置，确认当前行为、预期结果、实现缺口、非目标及必须保留的契约。记录源码基线和已有改动；没有 Git 时使用实际文件信息。

明确交付终点及其验证，例如交付可审阅的工作区改动，或集成到指定项目/分支并验证。涉及集成时写清目标位置、执行责任与已有授权，将目标环境的验证纳入验收条件。沿用用户已有要求和适用项目约定；无法确定且影响交付时集中询问，不把 worktree 完成等同于原项目已可用。

区分事实、已确认决策、假设和待决策项。原始需求及已确认决策完整记录或提供可访问引用，为设计结论标明依据，使执行与验收不依赖规划对话。用户纠错时删除错误前提，维护当前有效方案。

常规实现选择由规划者根据证据解决；影响产品语义、范围或授权的缺失信息才询问用户。无法访问必要资料时说明证据缺口，按影响范围处理：

- **局部阻塞**：标记受影响任务、后续依赖及解锁条件，只为不受影响的任务生成可执行方案和启动 Prompt。
- **整体阻塞**：缺口影响整体目标或没有独立可执行部分时，只交付事实基线、待决策项及影响，不生成占位任务卡或开工 Prompt。

## 2. 设计与任务拆分

按任务的依赖、风险和不确定性调整方案深度，给出一条有依据的实施路径，写清修改位置、调用或数据流变化、具体规则、边界行为和复用点。关键架构与语义判断在派发前完成；执行 Agent 可处理不改变既定设计和契约的实现细节。

- **小范围、逻辑明确**：一个实现与自测任务，另做独立验收，用简短方案说明改动和验证。
- **多个独立交付物**：分别拆任务，明确依赖和共享修改点。
- **大规模重复工作**：共用处理规则与验收要求，按目录、模块或数据批次组织，不逐文件复制任务卡。
- **跨阶段或存在未知因素**：先确定整体目标、需求覆盖、关键契约、阶段依赖和完成条件，再细化就绪阶段；后续阶段记录待解决问题、解锁条件及补齐设计的责任人。

仅在能减少上下文负担、明确写入责任或形成独立可验证产物时拆分。使用稳定任务 ID（如 `T01`），每项写清以下信息；小任务可用短段落，共同信息引用一次即可：

| 字段 | 内容 |
| --- | --- |
| 目标与交付物 | 对应需求和验收 ID、可核对的结果 |
| 输入与依赖 | 文件/符号、资料、前置产物、解锁条件及阻塞项 |
| 修改范围与步骤 | 允许修改或新增的位置、唯一写入者、已确定的实施规则 |
| 验证 | 工作目录、环境前提、命令或操作、预期结果 |
| 执行约定 | 当前角色、允许派发对象、回报对象、模型及实际推理参数、必要工具、停止条件；返工关联原问题与尝试记录 |

无冲突的就绪任务可并行。重叠写入、未稳定契约、互斥运行资源和真实前置依赖需要串行；共同读取或使用稳定契约不构成串行理由。共享修改点指定唯一写入者，必要时安排集成任务。

相关测试随实现安排，优先复用或扩展现有测试；新增测试对应未覆盖行为或明确回归风险。只有独立工作或验证价值才另拆测试任务。

## 3. 模型与宿主能力

以入口已读取的模型参考作为角色模型配置、选择优先级、派发适配和本地记录格式的唯一来源。记录已选定的 `strategist` 模型与档位；分别确定新执行任务协调者、普通及复杂实施或诊断子 Agent、独立验收子 Agent 的模型与档位，已有执行任务保留其设置。规划与执行角色的配置由对应调用方落实到实际运行或派发参数，Prompt 本身不切换模型。宿主可提前只读探测；在任务的工具、输入类型和上下文需求明确后，按 reference 核对各角色的完整派发参数组合与执行条件，将确定的模型、档位、接口参数、上下文传递方式、简短理由、限制及已授权的失败后规则写入方案。未明确授权升档时，不在失败后自行升级。

本地模型记录按上述 reference 作为可选诊断快照保存，常规规划无需创建。在方案中说明未解析能力，以及要求保存但未成功的情况。

宿主没有子 Agent 派发能力，或必要派发条件经调整仍无法满足时，为受影响环节提供手动会话 Prompt，写清顺序和用户推进步骤。独立验收的接续 Prompt 须包含权威方案、待验收产物位置与版本、对应 AC、必要验证及证据要求，并说明将结果交回协调者更新原执行记录；验收者仍须未参与产物制作，在独立上下文中验收。模型、参数或其他必要条件尚未确认时列出前置条件，手动接续不消除这些阻塞；需要手动接续的范围不标为可自动执行。

## 4. 执行与验收协议

将本节适用规则完整写入交接方案，作为执行协议；启动 Prompt 引用该协议。

### 分工与派发

- **协调者**：统一派发、集成、维护执行记录并处理升级。
- **任务角色**：按任务能力、输入、产物及读写范围设置；职责相近且无分离需要时合并，角色数量与 Agent 实例数量分别按职责和就绪工作量确定。
- **独立验收者**：由具备相应能力、未参与被验收产物制作的 Agent 担任，在独立上下文核对权威资料及实际产物，不只采信制作方摘要，不修改验收对象。可合并验收同批任务。

派发层级固定为“执行协调者 → 子 Agent”：协调者直接派发实施、测试、诊断及独立验收 Agent；子 Agent 不创建子 Agent 或独立任务，需要拆分或调整设计时向协调者回报证据与建议。协调者不自行创建新的 Commander 或执行协调任务。由 Commander 编排时向指定 Commander 回报，Strategist 单独使用时向用户回报；模型变化不改变这些角色权限。

每次子任务派发明确当前角色、任务范围、无继续派发权限及具体回报对象，并携带关联问题的尝试记录与适用限制。只传任务所需上下文及可访问的协议引用，不把协调者启动 Prompt 当作子任务指令原样下发，也不将上级授权视为子 Agent 的派发授权。

执行会话启动及实际派发前复核方案中的接口、完整参数组合、上下文隔离和派发条件，传入任务卡、权威资料及必要上下文。将子 Agent 的模型与档位落实到派发参数，不仅写在任务文字中；核对上下文继承方式，避免意外继承协调者模型。宿主或能力变化时按方案携带的适配规则重新核对，调整执行安排。记录请求模型、档位与宿主实际回报，未回报则标明未知；不符时报告差异，按已授权规则处理，不静默替换。

并发受独立就绪任务数、用户指定的上限和宿主剩余名额共同约束，按宿主口径计算占用；上限未知时先串行，每次派发仍须满足宿主前提。

### 验收标准与证据

为验收标准设置稳定 ID（如 `AC01`），明确前置条件、输入/操作、预期结果、验证方式及证据，维护 `需求 → Txx → ACxx → 证据` 的对应关系，保留独立需求及层级。

1. 核对方案与标准是否覆盖原始需求及已确认决策。遗漏、矛盾或错误交由协调者按升级规则修正，不能以符合错误方案判定通过。
2. 停止对待验收产物的写入，用提交、文件摘要或快照标识实际内容；有未提交修改时不能仅用 HEAD。其他不冲突任务可继续。
3. 独立检查实际差异并运行必要验证，记录产物版本、逐项 AC 结果、命令/操作及证据。区分静态检查、测试和实际运行，未执行项标为未验证。
4. 交付前核对产物与验收版本一致。产物或前置依赖变化时，协调者确定受影响的任务和 AC，更新其状态并安排必要的重新验收；影响尚未查明时，暂停使用已变化输入的任务及其完成判定。

只有范围内任务经独立验收、最终集成状态满足全部必需 AC、本轮引入的差异均属于授权范围，且基线已有的无关改动保持原样、证据完整，才能宣布目标完成。必需验证缺失或只完成部分就绪任务时，报告已完成部分与剩余阻塞；范围调整须有用户明确授权。

### 进度、恢复与升级

协调者维护唯一执行记录，包含 `任务 ID | 负责人/模型 | 状态 | 产物版本/证据 | 阻塞原因/下一步`。状态为 `TODO → RUNNING → VERIFYING → PASS`；失败进入 `REWORK`，缺条件进入 `BLOCKED`。`PASS` 必须有独立验收证据，返工或解锁后按流程恢复。

子 Agent 回报任务 ID、产物、验证结果、证据及阻塞。协调者在派发、验收、返工、阻塞和完成时维护记录，每次完整回报前依次完成：

1. 保存可追溯的独立验收原始命令或操作、退出状态及输出，关联产物版本与 AC；已有可访问的原生输出可直接引用，不用摘要冒充原始输出，也不要求重复复制日志或重跑仍有效的验证。
2. 依据已核实事实原位更新需求、任务、AC 与证据的对应关系，以及当前轮次、方案与产物版本、状态、累计尝试和在途工作。当前任务表中 `PASS` 行的下一步置为“无”，后续阶段与未满足 AC、最终集成等剩余工作集中到当前整体下一步。阶段切换时移除旧阶段的“当前”标识，历史保留原轮次事实；不以追加 PASS 代替更新当前结论，也不以单项 PASS 宣布整体完成。
3. 实际回读记录及其引用的原始输出，确认存在、可访问，且证据适用于当前实际产物版本；同时核对累计尝试与仍在进行的动作，不将未知次数写成 0 或将进行中的工作写成无在途。证据缺失、版本不符或记录未同步时保留具体缺口，不宣布交接齐全或目标完成。
4. 完整回报实际工作区、产物位置与版本、逐项验收结果及证据入口、未验证项、累计尝试及新增证据、剩余工作、阻塞和在途工作；简短说明实际派发的任务与请求模型，未派发时说明原因。

续接先核对方案、记录、实际工作区和在途 Agent，按上述事实核对与更新要求恢复当前状态，避免重复派发。规划阶段仅指定记录位置，不创建空记录。

失败后在原执行记录中按稳定问题标识关联任务与 AC，维护修复及诊断的累计次数、每次方法与结果证据、剩余缺口、适用限制和下一步。一次修复尝试包括实施该方法及验证，实际诊断单独计次并纳入同一问题的总尝试；开始时登记，结束时补结果，中断或结果未知也保留已启动尝试，恢复同一次在途工作不重复计次。等待、状态查询和进度回报不计次。状态更新、阶段切换、重新规划、换模型、换 Agent、换窗口或任务拆分重命名均保留同一问题的累计次数与历史；不同的新问题分别记录，不靠改名或改称诊断重置计数。

失败后的下一次动作必须说明：上次新增事实、这次改变的方法或尚未排除的原因、预期证据，以及继续或停止的判断条件。AC 缺口缩小、具体原因被排除或必要前提得到补齐可作为进展；有进展且未触及适用限制时继续修复与验证。日志增多、改写描述或换执行者本身不算进展。重复失败且无进展时停止重复派发，由协调者评估尚未执行且有信息价值的诊断；有则执行并记录，无则交回规划者或用户，说明阻塞与恢复条件。设计前提失效时带证据修订，其他已授权、未触及适用限制且不受阻任务继续。

沿用用户已有尝试或预算限制；需要进一步控制消耗时在方案中明确上限、计数口径及适用范围（单问题、任务或整体目标），不统一写死次数。没有数值上限仍执行上述无进展停止规则。达到上限后停止受该限制约束的派发并报告未完成范围与恢复条件，不自行重置或提高上限；单问题上限不阻止其他独立工作，整体上限则适用于全目标。只有宿主提供可信用量时才按真实 token 或费用判断；必要预算无法核实时说明缺口，与用户确定可核实的限制，不以尝试次数冒充精确费用控制。

有相应能力与授权的协调者可在既定范围和产品契约内修订方案、补齐已解锁阶段；否则交回规划者或用户，相关任务保持阻塞。因失败修订时说明需改变的设计前提及证据，不能仅因失败重写方案再从头尝试。修订需更新方案版本、受影响任务及验收状态，保留关联问题的历史与限制，不擅自扩大模型候选范围或放宽验收要求。

## 5. 交付方案与启动 Prompt

按本次交付范围及项目文件规则保存方案。小任务用简短文档，多任务附任务信息；跨阶段按需拆分总方案与阶段方案，明确入口和阅读顺序，在总方案统一追踪需求。已有资料引用复用，不填充空章节。

交付前确认所有需求均有记录，并按范围检查：

- **就绪范围**：执行者无需规划对话即可找到目标与非目标、交付终点及验证、权威需求、事实基线、设计、任务依赖、角色模型、验收条件、执行协议及首批任务；该范围内每条需求有任务和验收对应。
- **阻塞或未就绪范围**：保留需求与已知事实，写清待解决问题、影响范围、解锁条件及责任人，不为满足检查而生成占位任务卡或验收标准。整体阻塞时按第 1 节交付，不要求首批任务或开工 Prompt。

聊天中给出方案入口、可执行范围、阻塞项及环境待查项。有就绪任务时提供填好真实信息的启动 Prompt，聚焦方案位置与版本、本轮范围和补充约束、执行记录与回报要求；模型参数及完整协议引用方案中的对应位置。目标环境无法访问方案时，先提供可访问的交接内容，或在 Prompt 中内联本轮所需方案内容及适用协议，再判定就绪。以下为自动派发场景的骨架，按当前能力调整，交付时不得保留占位字段：

```text
请依据以下交接方案完成本轮范围内的全部任务，按依赖逐批推进。
目标：<原始目标>
项目：<实际路径>
交付终点及验证：<最终位置、完成条件；涉及集成时注明执行责任、已有授权及目标环境验证>
权威方案：<可访问的位置及版本>
执行记录：<按项目规则确定的位置，执行开始时创建或续用>
本轮范围与首批任务：<执行范围及首批 Txx>
剩余阻塞：<受影响任务及解锁条件，无则写无>
执行约定：<方案中角色模型、派发适配、执行协议和验收要求的具体入口>
尝试记录与限制：<已有问题记录入口、适用上限；首次执行无历史或无数值上限时据实说明，仍执行无进展停止规则>
回报对象：<编排此目标的 Commander 标识；单独执行时为用户>
```
